## Review — Isolate frame output directories from earlier runs

**PR:** [#18](https://github.com/tugudush/video-analyzer/pull/18) · head `12-p2-isolate-frame-output-directories-to-avoid-stale-results` → `main` · one commit (`df5ce51`) · closes [#12](https://github.com/tugudush/video-analyzer/issues/12).

**Verdict: approve, with minor suggestions.** The fix sits in the right place. [`extractFramesOperation`](../../src/operations/extractFrames.ts:118) now asks [`createArtifactDir`](../../src/operations/shared.ts:80) for a folder and treats a caller-supplied `outputDir` as its _parent_, so the directory that [`listFrames`](../../src/services/ffmpeg.ts:244) enumerates holds only what this invocation wrote — which is the invariant `totalFrames`, `offset`/`maxImages` paging and `truncated` were already assuming. Both halves of the finding are closed by the same change: earlier frames are no longer counted (they live in a sibling folder) and no longer overwritten (the new run's numbered files start in an empty directory). The guard in [`assertEmptyFrameDir`](../../src/services/ffmpeg.ts:222) is defence in depth rather than the fix, and the three places that describe the parameter — [`operations.md`](../../skills/video-analyzer/references/operations.md:172), the input schema's `.describe` (`extractFrames.ts:68-73`), and the finding's status paragraph in [`codebase-review.md`](../../docs/reviews/codebase-review.md:64) — were all updated with it. On this branch `npm run check` is green: `typecheck`, `lint`, `format:check`, and `test` at 160 passed / 12 skipped.

Scope note: `outputDir` changes meaning from "the folder frames are written into" to "the parent of the folder frames are written into". Nothing breaks for a caller that reads `data.outputDir` or `images[].path`, but a caller that passed `outputDir` and then listed that path itself now finds a subfolder instead of JPEGs. That is the whole point of the fix, and it is documented in the two places an API caller would look, so this is a compatibility note rather than a defect — worth a line in the changelog or issue comment if anyone scripts against the old shape.

**Status: resolved.** Items 1–6 were addressed in `735dea7` on this branch. Re-verified after the fixes: `typecheck`, `lint` and `format:check` green, `test` at 161 passed / 12 skipped (`tests/unit/extractFrames.test.ts` now has 18 tests, one of them new). Each item keeps its original wording, followed by how it was resolved; the line references point at `df5ce51`, the commit that was reviewed.

### Should fix (small)

Every prior PR in this series refreshed that paragraph, and this one edits the file directly above it, so the mismatch is easy to miss. Re-run `npm test` and update the sentence (`160 passed, 12 skipped`, `ten local-media integration tests`). **Resolved:** the paragraph now records `161 passed, 12 skipped` and "the ten local-media integration tests" — 161 rather than 160 because resolving item 2 added the `even`-mode guard test.

### Worth considering

2. **`assertEmptyFrameDir` cannot fire from `extract_frames` today, and only half of it is tested.** `createArtifactDir` always appends `frames-<timestamp>-<uuid>` to the base (`shared.ts:86`), so the directory handed to `extractFramesEvenly` (`ffmpeg.ts:260`) and `extractFramesAtInterval` (`:325`) is freshly created and empty; the guard is reachable only by a direct caller of the exported helpers, and `src/` has no such caller besides the operation (`src/index.ts` does not export the ffmpeg module). Only the interval path has a test (`tests/unit/extractFrames.test.ts:385`). Either keep it and say plainly in the comment that it is an internal invariant for future callers — with one `even`-mode case so both call sites stay covered — or drop it and let the fresh folder be the single guarantee. Two details lean toward narrowing it: the `hint` ("use a new folder (or a new subfolder) per run") is addressed to someone who can choose the directory, which no `extract_frames` caller can, and the `INVALID_INPUT` code is not in the failure table in `SKILL.md`. The `ENOENT` branch is likewise unreachable, since the directory was just created. **Resolved:** the comment now states that this is the invariant that makes `listFrames` trustworthy and that `extract_frames` cannot trigger it, the hint is addressed to a caller that owns the directory ("Pass a directory this extraction owns; extract_frames always creates one per request"), and `tests/unit/extractFrames.test.ts` gained an `even`-mode case so both call sites are covered. The `ENOENT` branch stays as the one path a direct caller can exercise, and the guard's JPEG-only filter is now documented.

3. **The overwrite half of the finding is guarded on two of four extraction paths.** `extractFramesAtTimestamps` (`ffmpeg.ts:369`) writes `frame-0001.jpg` … into whatever `outDir` it receives, and `extractSceneFrames` delegates to it, so nothing refuses a pre-populated directory there. Through the operation this is fine — every mode gets a fresh folder — but the PR body's "the ffmpeg helpers also refuse a directory that already holds frames" is true only of the two _listing_ helpers. If the guard is meant to be a contract of `FrameExtractionOptions`, all four entry points should enforce it; if the fresh folder is the contract, none need to, and the options comment (which currently explains the rule in terms of "even and interval … list the directory afterwards") should say so. Pick one, since the asymmetry is the kind of thing a later caller reads as an oversight. **Resolved:** the fresh folder is the operation-level contract, and the guard is documented as a listing-specific invariant: `FrameExtractionOptions.outDir` now spells out that `even`/`interval` refuse a used directory while `timestamps`/`scene` leave that guarantee to the caller, and `extractFramesAtTimestamps` states that its positional names overwrite in place. The PR description was narrowed from "the ffmpeg helpers" to the two listing helpers.

### Nits

4. **`createArtifactDir` trusts its `baseDir` to be absolute.** The single caller resolves it first (`extractFrames.ts:121`), so `data.outputDir` stays absolute today, but the helper itself would happily `path.join` a relative parent and return a relative artifact path — and `data.outputDir` is documented as the folder actually written, next to `images[].path`, which callers expect to be absolute. Resolving inside the helper (or documenting "must be absolute") keeps the guarantee with the function that promises it. **Resolved:** `createArtifactDir` resolves both roots itself, so the returned path is absolute whoever the caller is, and `extract_frames` now passes `input.outputDir` through unchanged.

5. **The README and Skill examples now read as if the given directory is the destination.** `README.md:244` and `skills/video-analyzer/SKILL.md:103` both pass `"outputDir":"./frames"`, which now yields `./frames/frames-mwbx…-…/`. Nothing breaks — the response carries `data.outputDir` and absolute `images[].path`, and the Skill already tells the agent to report the exact paths — but one clause ("frames land in a subfolder of it") would make the examples match `operations.md`. **Resolved:** the README example comment now reads "(a new subfolder of ./frames)", and the Skill's "Grab frames" section states that `outputDir` names the parent and that `data.outputDir` / `images[]` report the files actually produced.

6. `frameDirOf` (`tests/unit/extractFrames.test.ts:118`) and `runDir` (`tests/integration/localMedia.test.ts:15`) are the same one-line accessor under two names. `data.outputDir` is now load-bearing for every frames assertion, so one shared helper would be reused by the next test that needs it. **Resolved:** both suites import `artifactDirOf` from the new `tests/helpers/results.ts`, and the two local copies are gone.

### Nice touches

- One change fixes both halves of the finding — the miscount and the silent overwrite — instead of patching `totalFrames` to subtract stale files.
- `data.outputDir` names the folder that was actually written, so a caller never has to reconstruct `frames-<stamp>-<uuid>` to find its frames.
- The reuse test asserts in both directions: the second run reports its own 3 frames, and the first run's folder still holds all 10.
- The unrelated-JPEG case is the one that pins the original regression — a `screenshot.jpg` in the parent is neither counted nor disturbed.
- The guard runs before `ffprobe` and `ffmpeg` (`ffmpeg.ts:260`, `:325`), so a rejected run costs no subprocess.
- Reusing `createArtifactDir` with an optional parent keeps one naming scheme for artifact folders instead of inventing a second path-shaping helper.
- The zod `.describe`, `operations.md` and the `codebase-review.md` status paragraph all state the new meaning, and the status paragraph records coverage rather than asserting the fix.
