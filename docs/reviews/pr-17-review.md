## Review — Enforce Gemini timeouts and cancellation end to end

**PR:** [#17](https://github.com/tugudush/video-analyzer/pull/17) · head `11-p2-enforce-gemini-timeouts-and-cancellation-end-to-end` → `main` · one commit (`9466e0d`) · closes [#11](https://github.com/tugudush/video-analyzer/issues/11).

**Verdict: approve, with minor suggestions.** The bounds are applied at the layer that matters. Every Gemini call now goes through [`GeminiMediaService.request`](../../src/services/gemini.ts), which derives one composite signal from the caller's signal and a per-call deadline, hands that signal and the deadline to the SDK, and enforces the same deadline in [`runWithBounds`](../../src/utils/abort.ts). I checked the installed SDK declarations rather than trusting the compiler: `UploadFileConfig`, `GetFileConfig` and `GenerateContentConfig` each declare both `abortSignal` and `httpOptions`, and `HttpOptions.timeout` is documented as a request timeout in milliseconds, so `sdkRequestConfig` maps onto fields the client actually reads instead of extra properties TypeScript happens to tolerate. The upload budget now starts before the upload (`gemini.ts:305`) and each poll sleeps for `Math.min(pollIntervalMs, remaining)` (`:370-372`), which closes both halves of the finding: the clock starting late, and a stalled status read outliving the deadline. `runWithBounds` has the right shape for a client that ignores the signal — it races the work against the deadline and rejects even when the work never settles, which is exactly the probe case the finding recorded.

Two small things before merge: the "raise X" hint names only one of the two variables that can be the binding budget, and `troubleshooting.md` promises a Ctrl-C cancellation message that the CLI cannot currently produce.

Scope note: cancellation is reported as `GEMINI_TIMEOUT` rather than a new code. That was already the house rule — `toVideoAnalyzerError` maps `AbortError` to `GEMINI_TIMEOUT` (`src/utils/errors.ts:66-70`) — so the PR extends an existing contract instead of creating a second one. The three resulting messages are distinct and documented, which is what a caller needs in practice.

**Status: resolved.** Items 1–5 were addressed in `b9846c8` on this branch; items 6–8 and the nits were not selected and remain open. Re-verified after the fixes: `typecheck`, `lint` and `format:check` green, `test` at 157 passed / 11 skipped (`tests/unit/geminiService.test.ts` now has 21 tests, `tests/unit/cli.test.ts` 15). Each item keeps its original wording, followed by how it was resolved; the line references point at `9466e0d`, the commit that was reviewed.

### Should fix (small)

1. **The timeout hint names a variable that cannot always help.** `requestTimeout(stage, timeoutMs)` at `src/services/gemini.ts:191-201` always says "Raise `VIDEO_ANALYZER_REQUEST_TIMEOUT_MS`". But `request` applies `effective = Math.min(config.requestTimeoutMs, budget)` (`:472-473`), and for the upload and status stages `budget` is the remaining `VIDEO_ANALYZER_UPLOAD_TIMEOUT_MS` (`:305`, `:382`). With `VIDEO_ANALYZER_UPLOAD_TIMEOUT_MS=60000` and the default request timeout, a stalled upload fails as "Gemini did not respond within 60000 ms (upload)" and tells the user to raise the request timeout — which changes nothing, because `min(300000, 60000)` is still `60000`. The same applies to a status poll taken after most of the upload budget has elapsed. `troubleshooting.md:71` then overstates what the message can do: a stage message reports the number that ran out, not which knob controls it. Pass the binding source into `requestTimeout` (or have the hint name both variables), and reword that line of `troubleshooting.md` to match. **Resolved:** `request` now takes the stage's `budgetName`, picks the setting that actually bound the call, and passes it to `requestTimeout`, which reports it in both the hint and `details.variable` — so a 60 s upload budget tells the user to raise `VIDEO_ANALYZER_UPLOAD_TIMEOUT_MS`, while a call capped by the request timeout still names that one. `troubleshooting.md`, `configuration.md` and the README row all state that the shorter of the two bounds wins and that the hint names it.

2. **`troubleshooting.md` promises Ctrl-C cancellation the CLI does not implement.** `skills/video-analyzer/references/troubleshooting.md:79-81` says the cancellation message means "the caller gave up (MCP tool cancellation or Ctrl-C)". The MCP half is wired end to end — `mcpServer.ts:71` → `mcpTools.ts:89` → `execute.ts:27` → each operation's `ctx.signal`. The CLI half is not: `src/adapters/cli.ts:234` calls `executeOperation` without a `signal`, and nothing installs a `SIGINT` handler, so Ctrl-C terminates the process and that message is never produced. Either wire it (`const controller = new AbortController()`, `process.once('SIGINT', () => controller.abort())`, pass `signal: controller.signal`) — which also makes the CLI's own timeout reporting reachable — or scope the sentence to MCP. Given the doc already claims it, wiring it is the smaller change. **Resolved:** `CliIO` gained an `onCancel` seam whose default installs a `process.once('SIGINT')` listener; `runCli` creates an `AbortController`, passes `controller.signal` into `executeOperation`, and disposes the listener in a `finally`. Ctrl-C now unwinds the operation into the documented `GEMINI_TIMEOUT` envelope instead of killing the process, and `tests/unit/cli.test.ts` covers both the install/dispose cycle and the `SIGINT` listener behind it.

### Worth considering

3. **`checkActive` turns a per-call timeout into a silent re-upload.** `gemini.ts:292-296` swallows everything the status request throws unless the caller aborted, and `:255` then deletes the cache entry, so a status check that exceeded `VIDEO_ANALYZER_REQUEST_TIMEOUT_MS` costs the user the timeout _and_ a fresh upload of a file that is probably still valid. The catch-all predates this PR, but this PR is what makes a swallowed timeout reachable, and "re-upload" is now a decision the timeout has to express. At minimum log the swallow (`this.logger.debug`), and consider handling `GEMINI_TIMEOUT` distinctly so a stalled status endpoint surfaces instead of doubling the cost. **Resolved:** `checkActive` rethrows any `VideoAnalyzerError` — a timeout or a cancellation both describe the call, not the file — and logs anything else at debug before falling back to `null`. New test: a cached handle whose status request stalls fails with `GEMINI_TIMEOUT` and `uploadFile` stays at one call.

4. **A leader's cancellation poisons every follower sharing the upload.** `:264` creates the shared promise from the _leader's_ `params.signal`, and `:261` hands that same promise to followers. If caller A cancels, the upload request is aborted and caller B — which never cancelled — receives `GEMINI_TIMEOUT` "The Gemini request was cancelled." Coalescing existed before, but cancellation gives it a new failure mode with a message that misattributes the cause. Either keep the shared work independent of any one caller's signal and race each caller's await against its own signal (which `waitUnlessCancelled` already does for followers), or translate the rejection for followers. A two-caller test with one cancelling would pin whichever behaviour you choose. **Resolved:** the shared upload is now created from a copy of `params` with `signal` removed, and every caller — the leader included — awaits it through `waitUnlessCancelled`, so a cancel ends that caller's wait only; `inFlight` is cleared when the shared promise settles, not when the leader's wait does. New test: the leader cancels, the upload request's own signal stays un-aborted, and the follower still receives the `ACTIVE` handle from a single upload.

5. **The headline claim is only asserted for cancellation, not for the deadline.** The test "rejects an in-flight generation as soon as the caller cancels" asserts `call.signal.aborted === true`, but the fake-timer deadline tests assert only the error code. One extra assertion in "fails a stalled generation once the request timeout elapses" — capture the call, expect its `signal.aborted` to be `true` after advancing the clock — would prove that a deadline also tears down the request, not just that a caller does. **Resolved:** the stalled-generation test now captures the call and asserts its `signal.aborted` is `true` after the deadline elapses.

6. **`src/utils/abort.ts` ships without its own tests.** Its guarantees are observed only through the service: that `timeoutMs <= 0` disables the deadline (the `waitUnlessCancelled` path, exercised incidentally), that an already-aborted signal rejects before `work` runs (tested at the `ensureUploaded` entry point, `:245`, not at the helper), that the `abort` listener is removed, and that `isAbortError` recognises the three names it lists. A focused `tests/unit/abort.test.ts` is cheap and would make the module's contract explicit rather than emergent — it is the piece most likely to be reused by the next remote call.

7. **The `mcpServer` forwarding line is only covered by its type.** `tests/unit/mcpTools.test.ts` proves the descriptor forwards the signal; the change that feeds it, `tool.invoke(args, { signal: extra.signal })` at `src/adapters/mcpServer.ts:71`, rests on `RequestHandlerExtra.signal` being required. A cancellation test through the real `Client` would close the loop, but it needs a tool that stalls long enough for `client.callTool(..., { signal })` to interrupt, and the server may not deliver a response for a cancelled request — so this is a note rather than a request. Worth stating explicitly in the review or the code if it stays uncovered.

8. **A processing timeout leaves the file in Gemini.** `waitForActive` throws `processingTimeout`, and nothing tells Gemini to delete the upload, so the media lingers until its ~48 h expiry; retrying uploads it again. A best-effort delete on the timeout path needs a `deleteFile` on `GeminiApi` plus its fake, so it is outside this PR — but it is the natural follow-up to an end-to-end timeout story and deserves an issue rather than silence.

### Nits

9. `waitUnlessCancelled` passes `timeoutMs: 0` together with an `onTimeout` (`gemini.ts:500-502`) that can never run — and if it ever did, the message would read "Gemini did not respond within 0 ms (poll)". Dropping the option (or making it a deliberate `never`) keeps the two call sites honest.

10. `requestCancelled()` (`:203-208`) carries no `details`, unlike `requestTimeout`, which records `stage` and `timeoutMs`. An envelope produced by a cancelled upload therefore cannot say which call was cancelled.

11. `waitForActive` throws `processingTimeout` straight after the sleep when `now >= deadline` (`:375`), without a final status read. The last status read happened a poll earlier, so a file that turned `ACTIVE` during those final seconds is reported as a timeout. Reading once more when `remaining` was the shorter of the two would cost one request and let the deadline be the only thing that fails.

12. `tests/unit/geminiService.test.ts` — "abandons a stalled upload instead of waiting for it" never advances a clock; it asserts that cancellation wins over a pending upload. "aborts a pending upload when the caller cancels" describes what it checks.

### Nice touches

- `runWithBounds` rejects the awaited promise even when `work` ignores the signal, and the test proves it with a never-settling fake rather than an immediately-resolving one — which is precisely what the original finding asked for.
- One composite signal is handed to the SDK, so the transport is torn down instead of abandoned, and the same signal is what `runWithBounds` races against — one source of truth for both bounds.
- `Math.min(this.config.requestTimeoutMs, budget)` lets a per-stage budget shorten a call but never lengthen it past the configured request timeout, so the two settings compose instead of fighting.
- `checkActive`'s rethrow (`:293-294`) is the subtle case: without it, a cancelled caller would fall through to a fresh upload.
- The upload budget starting before the upload, and the poll sleeping for the smaller of the interval and the remaining budget, are the two smallest possible changes that make `VIDEO_ANALYZER_UPLOAD_TIMEOUT_MS` mean one thing.
- Reusing `GEMINI_TIMEOUT` keeps the error model stable, and the three messages are distinct enough for the troubleshooting doc to branch on.
- README, `configuration.md`, `troubleshooting.md` and the `codebase-review.md` status paragraph all describe the same two budgets, and the status paragraph states the coverage rather than asserting the fix.
